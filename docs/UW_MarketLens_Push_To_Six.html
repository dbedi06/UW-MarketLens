DYOP · S3 Anomaly Model · Post-mortem & Roadmap

Path to a genuine 6/10

An honest read on where the model stands and what it would actually take to move it.
Companion to UW_MarketLens_Implementation_Plan.html · Spring 2025

This document is local to the project, not a public deliverable. It exists because the main implementation plan briefly claimed an honest 6/10 rating for the S3 anomaly detector after the Phase A push. The current measured rating is about 6.0/10, with the remaining risk coming from the small sample size. Below: what was overclaimed, what is genuinely in place, and what each remaining half-point on the rating actually requires.

1Where we honestly are

6.0
Today (post-v0.9). Detector now trains on a real 54-market Polymarket corpus; the synthetic fallback is for contributors who haven't built the pickle. Reference distribution reflects real score ranges. The labeled-eval plumbing is complete and the current verified set contains 12 cases with a measured AUC of 0.672 and a wide CI.
6.5
Reachable with Phase B. A larger verified labeled set (N ≥ 20), cached real-market corpus (≥ 50 markets), retrained detector, non-circular sybil injector, labeled eval re-run. Reports a real AUC with its CI — whatever that AUC turns out to be.
7–8
Phase C and beyond. Per-case SHAP attribution exposed to the frontend "why" panel, time-series CV harness, a small supervised tier on triaged alerts. ≥ 100 labels for any of these to mean much.

2What the 6/10 framing got wrong

Claim madeWhat's actually true
"Sybil-ring AUC: 0.472 (base) → 0.906 (network-aware) — the operative lift number." The sybil_ring injector perturbs exactly the four network-feature columns the new code added, and leaves the five base feature columns near-clean. The network-aware model wins because the test was designed to favor it. This is the same self-injection-matches-inductive-biases circularity Section E of the plan calls out as a known limitation. The number is real arithmetic; it is not evidence of detection skill on real sybil rings.
"Seeded 10 candidate labeled cases against rubric v1." The evidence URLs (FT, The Block, X, CoinDesk) were generated from author intuition without verification. Several almost certainly do not resolve. They were marked LK-candidate with a CANDIDATES.md note saying "review before quoting," but feeding unverified entries into a labeled-eval pipeline is exactly how a synthetic-looking number gets quoted as evidence. Those seed entries were removed from the released file; the current set now contains 12 verified cases under rubric v1.
"Every column the live route shows the detector is a column the detector trained on." True — but only in a synthetic sense. Both the training data and the scored data go through feature_matrix_streams_with_network; the training input is still clean_streams_with_network with hand-picked Beta distributions. A real Polymarket market may sit anywhere on those axes; we have no way to know without measurement.

3What is genuinely shipped

The plumbing. The code paths are correct, tested (124 passing tests), and ready to consume real data when it arrives:
  • from_trades_with_network() — base + network feature blocks from a RawMarket, with NaN fallback when wallet addresses are missing.
  • feature_matrix_streams_with_network() — one source of truth for column order; the live route and labeled-eval scorer share it.
  • anomaly.scoring.get_detector() — lazy-fit singleton; the live route and the labeled-eval scorer use the same model.
  • scripts/eval_on_labeled.py — bootstrap-CI ROC-AUC and a low_n_warning flag in last_labeled_eval.json.
  • scripts/seed_labeled_cache.py — one-shot cache warmer once labels exist.
  • data/labeling_rubric.md v1 (locked) + CANDIDATES.md labeling protocol.

4Phase B — gates to a genuine 6/10

The order below is what matters for the rating, not what's easiest:

B1. Verified labeled set (N ≥ 20, balanced)

  • Run python -m scripts.discover_labeled_candidates with NEWS_API_KEY set — appends LK-candidate-v2 rows to labeled_cases.yaml from NewsAPI manipulation queries plus mundane samples from the v0.9 corpus.
  • Each labeler reads data/labeling_rubric.md v1 before verifying any rows.
  • For each controversial candidate, the evidence_url is personally opened and confirmed to meet the rubric's evidence standards. Prefer an archive.org snapshot so the link stays stable.
  • If evidence cannot be produced to standard, the market is dropped, not downgraded to mundane.
  • At least two labelers cover at least two shared markets so Cohen's κ has something to compute.
  • Target balance: ~10 controversial / ~10 mundane minimum.

Why this gates the rating. Without verified labels there is no cross-check on the synthetic eval. We're stuck reporting "the model wins on patterns we designed it to win on," which is what 4.5/10 captured. After v0.9 the detector finally learns from real data, and the current AUC headline is filled by verified labels; the remaining work is to stabilize that estimate with more cases.

B2. Cached real-market corpus (≥ 50 resolved markets) — DONE in v0.9

  • scripts/build_real_corpus.py fetches top-N resolved Polymarket events via Gamma + Data API + optional Polygon enrichment. Saves JSON snapshots to backend/app/anomaly/data/corpus/.
  • Local corpus has 54 distinct resolved markets with non-trivial trade tape (median ~280 trades / market).
  • Corpus JSONs are gitignored; the trained pickle (trained_model.pkl, ~1.3 MB) is committed so the model is reproducible without re-fetching.

What landed. train_from_corpus() fits the IsoForest on the real per-market feature matrix instead of clean_streams_with_network. Reference distribution and per-column network medians come from real markets. get_detector() loads the pickle on import; the synthetic path is now a fallback only.

B3. Non-circular evaluation

  • Add a sybil_ring_v2 injector that also nudges base features moderately (volume +20-40%, traders -10-20%, spread −10-20%) so the lift demo isn't purely on the columns the new features target.
  • Add a base-feature-only injector that the network-aware model should not win on — to demonstrate the new features don't break detection of patterns base features should still see.
  • Report both AUCs side by side in last_eval.json; document the comparison in MODEL_STATUS.md.

B4. Retrain on real corpus & re-run labeled eval — DONE in v0.9

  • IsoForestDetector now trained on the real corpus via scripts/train_from_corpus.py; synthetic remains as fallback via get_detector() resolution order.
  • Run scripts/eval_on_labeled.py --scorer app.anomaly.scoring:score_market_url against the verified label set.
  • Publish whatever ROC-AUC results, with its bootstrap CI. Do not tune to make the number higher — that's how synthetic-overclaim happens.
  • Update MODEL_STATUS.md with the real number and its CI; update the implementation-plan HTML bottom-line callout to match.
Honest expectation. The current measured AUC is 0.672 with a wide CI on the 12 verified cases; the honest target remains roughly 0.65-0.75 on N=20-30 labels. That's clearly better than chance on real data, but still not a production system.

5Phase C — gates to 7-8/10

Only worth attempting once Phase B has produced verified numbers; otherwise these add complexity on top of an unmeasured base.

CapabilityWhat it actually unlocks
Per-case SHAP attribution exposed via the live route. The frontend "why" panel currently shows placeholder text from mock.py. SHAP TreeExplainer over the fitted IsoForest gives per-feature contributions on the scored windows, so the reason a market got the score it did becomes auditable.
Time-series cross-validation harness. Train on markets resolving before date T, evaluate on markets resolving after T. The canonical way to surface dataset-shift weakness and produce a number that survives the "but in production..." critique.
Order-book / depth features. Polymarket's CLOB does not currently expose depth history at the granularity required for top-of-book imbalance, quote-flicker, or order-to-trade ratio. Either depends on a separate scraping effort over time, or stays deferred. Top of the list for production-grade work.
Light supervised tier on triaged alerts. A small gradient-boosted model on labeled alert outcomes, riding on top of the IF score. Requires ≥ 100 labels and an analyst pool we don't have. Documented for completeness; not realistic at project scope.

6What good looks like, end-to-end

# Phase B execution [B1] team labels ≥20 markets → labeled_cases.yaml (verified URLs) ↓ [B2] seed cache against labels + top-40 library ↓ # MARKETLENS_POLYMARKET_LIVE=1 backend/app/ingestion/cache/ (≥50 markets) ↓ [B3] add sybil_ring_v2 + base-only injectors ↓ [B4] retrain detector on the cached corpus ↓ python -m scripts.eval_on_labeled \ --scorer app.anomaly.scoring:score_market_url ↓ last_labeled_eval.json ← real ROC-AUC + bootstrap CI ↓ update MODEL_STATUS.md + plan-HTML bottom-line ↓ rating moves from 4.5 → 6 (or wherever the data lands)

7What this document is for

Two purposes. First, internal accountability: if anyone (us, reviewer, future self) opens the project six months from now and wonders "did the team actually do what it said?", the answer should be visible without needing to dig through commit history. Second, a runbook: when Phase B begins, B1–B4 are the task list. The pipeline already exists; what's missing is the data and the discipline to publish the number that falls out of it, not a prettier one.

One rule when Phase B runs. Whatever the real-data AUC turns out to be is the number that goes in MODEL_STATUS.md and the plan-HTML callout. We do not iterate the injector, feature set, or training distribution until the labeled number is published. That is how synthetic-overclaim happens: each iteration nudges the model toward whatever the test set says, and the headline AUC drifts upward without measuring anything new.
